# Hard 多 Session 开发协作架构

**状态：** 已确认  
**日期：** 2026-08-25  
**Phase F 合同修订：** 2026-08-29  
**适用范围：** Hard 的后续规划、开发、审计与发布  
**替代内容：** 替代原先“项目经理会话 + 单一执行会话”的协作方式，不替代现有产品运行架构

## 1. 架构决策

Hard 的产品代码继续保持一个 Git 仓库中的模块化单体：Vue 前端、FastAPI 后端、Git 管理的课程内容、SQLite 学习数据和本地 Runner。此次调整不拆微服务，只拆分开发职责和会话上下文。

不设独立 AI 模块 Session。AI 不是当前核心交付；未来若加入智能答疑、代码诊断或个性化路线，必须先由架构与管理 Session 创建 RFC，确认成本、隐私、离线降级和可验证性，再分配给现有专业 Session。

```text
可轮换的 Hard 项目策划 Session   # 面向用户、分发任务、汇总六方报告
└── Hard 六个专业 Session
    ├── 架构与管理 Session       # 规格、合同、依赖、范围审计
    ├── 后端 Session             # FastAPI、SQLite、学习引擎、Runner、服务端安全
    ├── 前端 Session             # Vue、交互、响应式、可访问性、客户端状态
    ├── 内容与课程 Session       # Python/Java/C#/C++ 课程、练习、来源和内容验证
    ├── 测试与审计 Session       # 独立复核、纵向 E2E、安全与视觉证据
    └── 部署与运维 Session       # D 盘工具链、启动包、备份恢复、LAN、未来 Docker
```

项目策划 Session 不计入六个专业 Session，也不直接写产品代码。它是可替换的总控入口：理解用户目标、选择主责 Session、发送详细任务、等待报告并请求用户做最终阶段决策。

## 2. 核心原则

1. **一个产品架构。** 各 Session 不得创建平行 API、第二套内容格式或重复状态模型。
2. **一个最终决策点。** 架构与管理 Session 提出专业结论，项目策划 Session 汇总，最终阶段放行由用户明确批准。
3. **按阶段批量布置。** 不再逐个 Task 发送零散指令；每次下发完整阶段任务包，包含全部上下文和验收条件。
4. **专业 Session 持久化。** 同一领域后续阶段优先复用对应 Session，避免每个 Task 重新解释项目。
5. **合同先行。** 跨端工作先冻结 API、内容 schema、错误码、ID 和迁移规则，再并行开发。
6. **证据代替口头完成。** 完成必须附提交、文件范围、测试结果、截图或覆盖报告、限制和剩余风险。
7. **未放行不得跨阶段。** 一个阶段可以批量执行，但阶段审计未通过前，不得准备、执行或安排下一阶段。
8. **共享仓库不共享未提交修改。** 并行写入必须使用独立 worktree/分支；若共用工作区，只允许一个写入 Session。

## 3. Session 职责与边界

### 3.1 架构与管理 Session

**职责**

- 保存产品目标、架构决策、当前进度、阶段基线和风险。
- 编写完整阶段任务包，明确目标、依赖、文件白名单、测试和停止条件。
- 审批 API、schema、数据库迁移、目录边界和跨 Session 变更。
- 审计提交链与验证证据，给出通过、修复或阻断结论。
- 维护 `TASKS.md`、设计规格和交接文档。

**禁止**

- 在审计时顺手修改被审计实现。
- 以自动化通过代替产品、视觉、安全或数据完整性判断。
- 在未完成当前阶段复审时布置下一阶段。

**主要文件**

- `TASKS.md`
- `docs/superpowers/specs/**`
- `docs/handoff/**`
- 跨域架构决策文档

### 3.2 后端 Session

**职责**

- FastAPI 路由、应用服务、错误协议、幂等和配置。
- SQLite/FTS5、SQLAlchemy、Alembic、事务与迁移安全。
- 评分、掌握度、复习、成长、搜索、备份、LAN 服务端和 Runner。
- 生成 OpenAPI 合同，防止参考解、隐藏测试和私密字段泄露。

**主要文件**

- `apps/api/**`
- `packages/contracts/openapi.json`
- 与后端合同直接相关的生成脚本

**边界**

- 不编辑课程正文。
- 不擅自改变前端体验；接口变化必须先获得架构 Session 批准。
- 产品逻辑变更先补失败测试，再做最小实现。

### 3.3 前端 Session

**职责**

- Vue 页面、路由、状态、设计系统、响应式和可访问性。
- 桌面 `1440x1024` 与手机 `390x844` 的功能一致性。
- API 客户端使用、离线草稿、错误恢复和用户可见反馈。
- 与视觉目标一致的真实数据界面，不以静态假数据冒充状态。

**主要文件**

- `apps/web/**`
- 前端单元测试和组件测试

**边界**

- 不手写偏离 OpenAPI 的私有接口类型。
- 不修改服务端评分或内容真相源。
- 视觉交付必须使用真实运行页面完成截图与审计。

### 3.4 内容与课程 Session

**职责**

- Python、Java、C#、C++ 的课程、课时、题目、挑战和分级测试。
- 来源目录映射、原创中文内容、概念依赖和内容覆盖率。
- 参考解与隐藏测试的服务端存储，以及真实对应 Runner 证据。
- 内容 schema、验证器、原创性检查和覆盖报告。

**主要文件**

- `content/**`
- `tools/content/**`
- `docs/content/**`
- `docs/audit/task-*/coverage.json` 与内容人工抽查记录

**边界**

- 不复制来源长段落、原测验、图片或评论。
- 不放宽 Runner 安全能力来迁就课程题目。
- 不修改产品 API/UI；发现能力缺口时提交给架构 Session 分流。

### 3.5 测试与审计 Session

**职责**

- 独立复核阶段任务包、提交链、文件范围和完成声明。
- 后端、迁移、内容、前端、E2E、Runner、安全和备份恢复验证。
- 桌面/手机真实纵向流程与视觉证据。
- 产出按 P0/P1/P2 分类的可复现问题，不直接掩盖失败。

**主要文件**

- `tests/**`
- `docs/audit/**`
- 经任务包授权的跨层 E2E 测试

**边界**

- 默认只读审计。需要修复生产代码时必须退回对应专业 Session。
- 不降低断言、阈值或删除失败测试来换取通过。
- 不把 Mock 测试当作真实纵向链路的替代品。

### 3.6 部署与运维 Session

**职责**

- D 盘工具链、统一检查脚本、本地启动包和环境健康报告。
- SQLite 备份/恢复运行流程、LAN 使用说明和端口生命周期。
- 发布清单、离线安装与未来 Docker 方案。

**主要文件**

- `scripts/**`
- `docs/setup/**`
- 发布、打包和部署配置

**边界**

- Docker 延后到明确需要时实施，不提前增加维护成本。
- 下载、写入 `D:\DevTools`、修改防火墙或暴露网络前必须取得用户授权。
- 不替代后端 Session 修改业务逻辑。

## 4. 阶段协作流程

```text
架构 Session 冻结阶段基线与合同
        │
        ├── 后端 Session ─────┐
        ├── 前端 Session ─────┤
        ├── 内容 Session ─────┼── 各自提交阶段交付与证据
        └── 部署 Session ─────┘
                              │
                       测试与审计 Session
                              │
                 架构 Session 最终复审与放行
```

### 4.1 阶段任务包必须完整包含

- 阶段目标及用户价值。
- 起始提交和允许的分支/worktree。
- 本阶段全部工作项，不使用只有标题的简单描述。
- 每个 Session 的文件白名单和禁止范围。
- 需要先冻结的 API、schema、ID、迁移和 UI 状态合同。
- 依赖顺序、可并行项和集成顺序。
- 明确的测试命令、阈值、真实证据和失败关闭条件。
- 高风险审批点：网络下载、工具安装、防火墙、正式数据迁移等。
- 阶段结束报告格式及“不得进入下一阶段”的门禁。

### 4.2 推荐集成顺序

1. 架构合同与内容/API schema。
2. 后端与内容真相源。
3. 前端客户端与交互。
4. 部署和运行流程。
5. 测试 Session 独立纵向复核。
6. 架构 Session 给出专业审计意见，项目策划 Session 汇总后由用户决定是否进入下一阶段。

## 5. Git 与并行规则

- 每个阶段记录一个不可变起始提交。
- 并行 Session 使用独立 worktree 和阶段分支，例如 `phase-e/backend`、`phase-e/content`。
- 同一文件只能有一个主责 Session；跨域生成文件在任务包中指定唯一生成方。
- 每个专业 Session 可以按阶段生成一个或少量有意义的提交，不要求每个 Task 单独停顿。
- 合并前必须通过该 Session 的专项检查；阶段末再执行全量检查。
- 工作区存在他人未提交修改时不得覆盖、清理、暂存或提交这些修改。

## 8. 项目策划 Session 轮换协议

以下任一情况出现时，可以重建项目策划 Session：

- 完成一个大阶段并准备进入下一阶段。
- 对话中出现大量重复背景、压缩后容易丢失门禁，或任务分发效率明显下降。
- 项目目标、Session 架构或任务计划发生重大调整。

重建前必须完成：

1. 更新 `docs/handoff/2026-08-25-hard-two-session-core-context.md` 中的当前 HEAD、工作树、阶段状态和门禁。
2. 将本阶段分发与六方报告保存到 `docs/handoff/`。
3. 记录六个专业 Session 的准确标题和会话 ID。
4. 写明尚未决定的问题、需要用户批准的动作和下一条允许执行的指令。
5. 创建新的项目策划 Session，让其只读加载交接文件并复述当前状态。
6. 确认新策划 Session 理解正确后，再归档旧策划 Session。

禁止同时让两个项目策划 Session 分发写入任务。交接期间旧会话只负责核对，新会话只读入职；切换完成后只能有一个总控。
