# Hard 项目会话任务总结内容规范

> 更新日期：2026-09-02

## 1. 目的

本规范用于统一 Hard 项目策划总控与六个专业会话的任务总结，使任何后续 Agent 都能在不重复读取整个项目的前提下，快速判断会话职责、已完成工作、当前门禁、验证证据和下一步允许动作。

本目录只覆盖当前有效会话：策划总控、架构与管理、后端、前端、内容与课程、测试与审计、部署与运维。已归档的“P001 | AI员工 | Hard项目执行”不再生成或维护任务总结。

## 2. 文件命名

- 规范文件：`00-会话任务总结内容规范.md`
- 会话文件：`NN-<会话昵称>-会话任务总结.md`
- 文件名中的昵称必须与 Codex 侧栏会话标题一致或能唯一对应。
- 一个会话只维护一份主总结，不按每次任务重复新建文件。

## 3. 固定内容结构

每份会话任务总结必须依次包含以下内容：

1. **会话身份**：项目、完整标题、昵称、会话 ID、当前状态、更新时间。
2. **会话定位**：一句话说明该会话为项目解决什么问题。
3. **负责范围**：列出允许负责的功能、目录或审计领域。
4. **职责边界**：明确不应自行承担的工作、必须等待的授权和跨会话限制。
5. **已完成任务总结**：按阶段记录任务范围、主要成果和审计结论。
6. **提交与工作树**：记录源提交、集成提交、分支、工作树及是否干净；没有提交时写“无产品代码提交”。
7. **验证证据**：只记录实际运行并看到结果的命令类别、测试数量、覆盖率、截图或审计报告。
8. **当前遗留与风险**：使用 P0、P1、P2 分类；没有阻断项时必须明确写零。
9. **后续可接任务**：只写与该会话职责相关且尚未开始的任务，不预先认领无关工作。
10. **交接与汇报要求**：说明接收任务包所需信息及完成报告必须包含的字段。

## 4. 单项任务记录格式

后续追加单项任务时，统一使用以下字段：

```text
### <阶段 / Task 编号 / 任务名称>
- 任务来源：
- 主责会话：
- 协作会话：
- 基线分支与 HEAD：
- 授权范围：
- 实际修改：
- 提交：
- 验证证据：
- 审计结论：
- 未覆盖项：
- 下一步：
```

禁止使用“应该通过”“大概完成”等推测性措辞。无法验证的内容写入“未覆盖项”，不得伪装成成功证据。

## 5. 状态和优先级

会话状态统一使用：`执行中`、`待复核`、`待命`、`阻塞`、`已归档`。

问题优先级统一使用：

- **P0**：安全、数据损坏或核心流程完全不可用，必须立即冻结阶段。
- **P1**：阶段验收条款未满足或主要用户旅程失败，修复前不得放行。
- **P2**：不阻断当前阶段，但必须记录的技术债、环境限制或后续增强项。

## 6. 证据与提交规则

- 必须区分“专业会话源提交”“集成分支提交”和“最终审计基线”，不得混写。
- 提交哈希至少记录 7 位；关键里程碑优先记录完整哈希。
- 测试报告必须包含退出结果、通过/失败数量及适用阈值。
- UI 审计应记录 viewport、真实 API 或模拟 API 属性以及截图目录。
- 不得在总结中记录密钥、令牌、真实个人数据、隐藏测试正文或参考答案。
- 工作树存在用户遗留或交接文件时，只记录并保护，不得清理、覆盖、暂存或提交。

## 7. 任务分发和门禁规则

- 默认始终启用上下文与 Token 优化：只读取当前任务真正需要的内容，只通知相关会话，避免重复背景、无关工具和无关命令输出；准确性仍优先于节省 Token。
- 所有任务由唯一策划总控判断主责会话，只发送给确有职责关系的会话，避免无关广播和 Token 浪费。
- 发给执行会话的任务文字必须以 `【发给 <Session 名称>】` 开头。
- 完整 E2E 只能由测试与审计会话启动；其他会话只运行自身范围内的测试，除非任务包另有明确授权。
- 专业会话不得自行进入下一阶段、扩大目录边界或修改冻结合同。
- 阶段是否放行由用户最终决定；“审计成功”不等于自动开始下一阶段。
- 用户消息以 `skiss`、`skiss:` 或 `skiss：` 开头时，按项目 `AGENTS.md` 启用技能与插件优先模式；该模式与默认 Token 优化同时生效。
